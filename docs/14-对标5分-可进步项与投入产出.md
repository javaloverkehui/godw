## 1. 先修正一个判断：BI 的差距被低估了

`13` 号文档写「语义层与 BI 4 分，缺自助 SQL 控制台与图表类型覆盖」。实读代码后，这个描述不准确：

矩阵的三个实现取舍：

1. **两次查询而不是一次 JOIN**：实例与任务是一对多，JOIN 后还要按实例去重，反而更容易写错；
   先取实例 id，再用 `ANY($1)` 一次取完任务。
2. **`Cells[nodeID]` 是与 `Runs` 等长的数组**，缺节点处为 `null`。这样某次运行少一个节点时，
   整列不会左移错位——前端也不用按 id 做二次查表。
3. **行按节点名排序**，不按分层。矩阵只回答「这个节点最近稳不稳」，行序稳定比「按层分组」
   更重要；两次刷新顺序不同会让人以为看错了表。

矩阵视图对运行态的价值：列表回答「这次运行成功了吗」，矩阵回答「这个节点最近稳不稳」。
后者是排查偶发失败与「从哪天开始变慢」的主要入口，靠翻列表一次一次点进去做不到。

口径说明：`work` 是事件处理本身的耗时（我们的成本），`frame` 是相邻两帧间隔（含 vsync 与合成，
天然有 1–2ms 抖动）。只拿 `frame` 卡 16.7ms 会把「浏览器节奏」当成「代码慢」，所以
「能否跑满 60fps」用 `work` 判，`frame` 只用来发现持续掉帧。

**本轮真跑才发现的两个 bug**（都是「不跑不会知道」的类型）：

1. **行级策略的占位符加了双层引号**：策略写 `region = '${user}'`（最自然的写法）时，
   替换后变成 `region = ''alice''`，SQL 语法错误。只有这条策略真的命中才会暴露，
   策略列表看起来一切正常。修法是先匹配「被引号包住」的形式，再匹配裸占位符；单测覆盖
   `'${user}'`、`${user}`、`O'Brien` 三种形态。
2. **空切片序列化成 `null`**：选择器没有「未覆盖模型」时返回 `"uncovered": null`，
   前端 `r.uncovered.length` 直接抛异常，预览框显示 `Cannot read properties of null`。
   服务端改为显式初始化空切片，前端同时加 `|| []` 兜底。

**问题一：分级枚举对不上。**
- 写入侧：`migrations/0004_governance.sql:21` 默认 `internal`，治理页下拉是 `public/internal/confidential/secret`（`assets/governance.js:191-195`）。
- 读取侧：`internal/meta/repo/compliance.go:105` 却按 `high/medium/low` 做 `CASE`。
- 结果：`DatasetClassification` 永远返回 `none`，`CheckExportApproval` 永远放行——**分级形同虚设**。

**问题二：审批没有入口。**
- `HasApprovedExport` 查 `export_job.status='approved'`（`repo/compliance.go:129`），但全仓没有任何代码把状态写成 `approved`，也没有审批路由。
- 结果：即使把问题一修好，high 级数据集导出会**永久 403**，因为没有「批准」这个动作。

**问题三：分类不按数据集基表算。**
- 现有 SQL 只判断「工作区里存在这个数据集」，`EXISTS` 子查询没有把 `column_policy.table_name` 和数据集的基础模型表关联起来。
- 结果：工作区里只要任意一张表命中高敏，所有数据集都会被判成同一级别。

修法：
1. 在 Go 里定义一份唯一映射：`secret → high`、`confidential → medium`、`internal/public → low`，SQL 的 `CASE` 从这份映射生成，不再两处各写一套。
2. 先取 `semantic_dataset.base_model` → 模型版本快照的 `table_name`，再查该表的列策略；不要用「工作区存在数据集」代替。
3. 增加 `POST /api/v1/exports/{id}/approve`（仅 admin），状态机 `queued → approved → running → success/failed`；治理页加「待审批」页签，批准/驳回都写审计。
4. 加一个「策略命中测试」：输入用户/角色/表，返回生效的行过滤条件与被脱敏的列，避免策略配了但没人知道会不会生效。

### 4.2 看板：让 BI 图表进看板

- `semantic.Card` 增加 `Chart string`（引用 `charts/{name}`），`metric` 保留兼容；校验时二选一。
- `RunCards` 对 `chart` 卡走 `Chart` 查询，返回 `type/encoding/points`；前端按 `type` 分派到柱/饼/指标卡/表格。
- 全局筛选（days/dim）同时作用到图表卡：图表本身有 `dataset`，把筛选作为查询参数透传。
- 编辑器先做「列表 + 上下移 + 宽度 + 全屏」的可视化操作，YAML 留在「高级」页签；不要一步跳到自由拖拽网格，收益小、回归面大。

### 4.3 SQL 控制台的安全边界

> **实现状态（2026-11-14）**：已落地，但有一处偏离——**没有启用数据库侧的只读事务**：
> `Connector` 抽象只暴露 `Query/Exec`，没有事务 API，而用不同连接执行 `BEGIN READ ONLY`
> 并不可靠。当前防线是：语法白名单（仅 SELECT/WITH）+ 单语句 + 写关键字黑名单（含 CTE 内的
> 数据修改）+ 15s context 超时 + 结果行数上限。
>
> 这挡得住误操作，挡不住刻意绕过（例如 SELECT 里调用带副作用的函数）。**生产环境必须给分析
> 账号只读权限**——这是唯一无法被绕过的防线。界面与响应里都写明了「行级策略不注入」。

必须同时具备，缺一条就不该放开：

- 只允许 `SELECT` / `WITH`，拒绝多语句与 DDL/DML；
- 只读事务（`SET TRANSACTION READ ONLY`）+ `statement_timeout` 15s + 结果上限 5000 行；
- 每次执行写审计（SQL 指纹、耗时、行数、命中策略）；
- 结果按输出列名套用列策略脱敏；
- **行级策略只保证「数据集模式」**：`SELECT ... FROM dataset_name` 由语义层编译，RLS 自动注入；原始 SQL 模式仅 admin 可用，并在界面明确写「行级策略不自动注入」。
  这一点必须诚实标注，否则就是给自己埋一个「看起来有 RLS、实际能绕过」的坑。

### 4.4 数据文档站

一页三栏，尽量复用现有接口，不新增存储：
