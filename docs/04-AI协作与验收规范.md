# 04 · AI 协作与验收规范

> 这份文档约束「怎么把这个项目交给 AI 做」。目标不是让 AI 写得更快，而是让它的产出**可合并、可回归、可追责**。

---

## 1. 一次只喂一张任务卡

把整个文档丢给 AI，它必然贪多求全、写出一堆跑不起来的骨架。正确做法：

```
你是一名 Go 后端工程师，正在实现 GoDW 数据仓库系统的 T0406 任务。

必读材料（按顺序）：
1. docs/03-核心抽象与接口.md 第 6 节（SQL 渲染与写入策略）
2. docs/02-元数据模型.md 第 4 节（幂等与重跑规则）
3. docs/tasks/E03-E04-模型与管道.md 的 T0406 卡片

约束：
- 只改 internal/sqlx/write.go 及其测试，不碰其他页面/模块
- 必须实现 6 种策略，不支持的策略返回 ErrUnsupported，不要静默降级
- 所有 SQL 生成必须走 dialect，禁止硬编码引擎语法
- 表驱动测试 + golden 快照，覆盖 4 引擎

交付：
- 变更文件清单
- 每个策略的实现选择（例如 ClickHouse 的 merge 用哪种方案，为什么）
- `go test ./internal/sqlx/...` 输出
- 你认为的风险点
```

**三条硬规则**
1. **上下文只给需要的**：一张卡 + 两张相关文档，不要给全仓库。
2. **边界写死**：允许改哪些文件，不允许动哪些。
3. **要求自证**：贴测试输出，不贴等于没做。

## 2. 编码红线

| 禁止 | 原因 | 替代 |
|---|---|---|
| 在 handler 里写业务逻辑 | 无法复用、难测 | handler 只做参数校验 + 调 service |
| 直接 `db.Query` 绕过 repo | 事务与租户隔离失效 | 走 repo / sqlc |
| 字符串拼接 SQL | 注入、方言错乱 | 参数化 + `QuoteIdent` |
| `fmt.Errorf("failed: %v", err)` | 丢堆栈、断链 | `errs.Wrap(err, code, msg)` |
| 无条件 `UPDATE state=?` | 并发下状态错乱 | 条件更新 + 影响行数校验 |
| goroutine 里用请求 ctx 却不处理取消 | goroutine 泄漏 | 派生 ctx + `defer cancel()` |
| 裸 `time.Now()` | 不可测试、时区错 | 注入 `clock.Clock` |
| 用 `float64` 存金额 | 精度丢失 | `decimal.Decimal` / 字符串 |
| 静默降级（不支持就当成功） | 数据错得无声无息 | 返回 `ErrUnsupported` |
| 前端 `any` 满天飞 | 接口一改就崩 | 用 OpenAPI 生成类型 |

## 3. 完成定义（DoD）

一张任务卡只有同时满足以下六条才算完成：

1. **代码**：实现任务卡「要点」中的全部条目，无 TODO 遗留（预留项须在卡上标注 `P2`）。
2. **测试**：核心包覆盖率 ≥ 80%，整体 ≥ 70%；异常分支有对应用例（不只是 happy path）。
3. **迁移**：涉及 schema 变更的，必须提供 up/down 迁移并本地验证。
4. **契约**：涉及 API 的，`openapi.yaml` 已更新且 `make api-gen` 无 diff。
5. **文档**：新增配置项、DSL 字段、错误码已写入对应文档。
6. **可观测**：关键路径有日志（含 request_id/instance_id）与指标埋点。

## 4. 测试矩阵

| 层级 | 范围 | 工具 | 门禁 |
|---|---|---|---|
| 单元 | 纯函数（编译、渲染、解析、状态机） | `testing` + 表驱动 | 覆盖率 ≥ 80% |
| Golden | 生成的 SQL / DDL / 图表配置 | `golden` 文件对比 | 变更需人工确认 |
| 集成 | repo、连接器、执行器 | testcontainers（PG/MySQL/CH）+ DuckDB | PR 必跑 |
| 契约 | API 与 OpenAPI 一致 | `oapi-codegen` + `oasdiff` | breaking 需标签 |
| E2E | demo 三条管道全链路 | compose + 断言 ADS 数据 | main 分支必跑 |
| 压测 | 调度吞吐、查询并发 | k6 + 自建脚本 | 里程碑验收跑一次 |
| 混沌 | 杀进程、断网、DB 切换 | shell 脚本 | M5 前完成一轮 |

**Golden 测试的纪律**：快照变化必须在 PR 描述里解释「为什么变」。不允许 `-update` 一把梭。

## 5. 阶段验收脚本

每个里程碑结束必须能跑通对应脚本，否则不算交付：

```bash
# M1 地基
make up && make migrate && godw doctor

# M2 元数据
godw datasource add --type postgres --name pg_main --dsn "$DSN"
godw datasource test pg_main
godw meta sync pg_main && godw meta tables pg_main | head

# M3 建模
godw validate -f warehouse/dwd_order_detail.yaml
godw apply -f warehouse/dwd_order_detail.yaml
godw ddl dwd_order_detail --env prod

# M4 管道
godw pipeline validate -f warehouse/daily_order.yaml
godw pipeline dry-run daily_order --bizdate 20251110
godw pipeline run daily_order --bizdate 20251110 --watch

# M5 调度
godw pipeline publish daily_order
godw instance list --pipeline daily_order --state FAILED
godw backfill daily_order --from 20251101 --to 20251107

# M6 质量与血缘
godw quality run dwd_order_detail --bizdate 20251110
godw lineage table dwd_order_detail --direction down --depth 3

# M7 BI
curl -s -X POST localhost:8080/api/v1/datasets/1/query -d '{"dimensions":["dt"],"measures":["gmv"]}'
```

## 6. 领域坑清单（AI 最容易写错的地方）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 时区混用 | 全链路存 UTC，展示按工作空间时区；`bizdate` 是「业务日」不是「自然日」，由调度器按配置时区计算 |
| 2 | 金额精度 | 统一 `DECIMAL(18,4)`，Go 侧用 `decimal.Decimal`，JSON 序列化为字符串 |
| 3 | 分区爆炸 | 分区粒度不得细于小时；按天/月分区；小文件合并策略写入维护任务 |
| 4 | ClickHouse 去重 | `ReplacingMergeTree` 查询需 `FINAL` 或 `argMax`，否则读到重复行；merge 策略必须在文档里写明 |
| 5 | 重跑产生重复 | 写入必须幂等；`append` 仅用于日志类不可变数据；其余用 `overwrite_partition`/`merge` |
| 6 | `SELECT *` 血缘 | 必须回查模型 schema 展开列，否则列级血缘全丢 |
| 7 | 大结果集 OOM | 一律流式（`Stream`/游标），禁止 `[]map[string]any` 全量加载 |
| 8 | 连接泄漏 | `rows.Close()` 用 `defer`；连接池按数据源隔离 |
| 9 | 调度双跑 | 多副本必须 advisory lock；唯一索引兜底 |
| 10 | 长事务锁表 | 分发/判定用短事务 + 批量；DDL 不在事务里等锁 |
| 11 | SQL 注入 | 值参数化，标识符白名单 + `QuoteIdent` |
| 12 | 日志泄密 | 密码/token 正则脱敏；SQL 参数打码 |
| 13 | 前端状态错乱 | 服务端状态交给 TanStack Query，本地 UI 状态才用 Zustand |
| 14 | 画布性能 | 连线批量更新、节点虚拟化，禁止每个节点一个 React 重渲染 |
| 15 | 权限漏判 | service 层必须再校验资源归属，不能只靠路由中间件 |

## 7. 评审清单（人工 review 用）

- [ ] 新增 SQL 是否都能在目标引擎执行（有没有 golden/集成测试）
- [ ] 所有状态变更是否条件更新
- [ ] 新接口是否带 workspace 过滤与权限校验
- [ ] 错误是否带错误码，能否被前端区分处理
- [ ] 是否有 N+1 查询（列表接口尤其）
- [ ] 大表操作是否走分区裁剪
- [ ] 新增配置项是否有默认值且写进示例配置
- [ ] 日志是否含上下文 ID，是否可能打印敏感信息
- [ ] 前端是否处理了 loading/empty/error 三态
- [ ] 破坏性变更是否影响已有版本与运行中实例

## 8. 如果只做 MVP：裁剪顺序

资源有限时，按以下顺序砍，砍掉的都不影响架构完整性：

| 保留（不可砍） | 可延后 |
|---|---|
| 元数据 + 4 连接器 | Doris/Hive/S3/Kafka 连接器 |
| 模型编译 + 分层约束 | SCD2、物化视图 |
| 管道 DAG + 6 写入策略 | 内置算子（先只留 SQL 节点） |
| 调度 + 重试 + 补数 + 日志 | 事件触发、传感器、资源组 |
| 质量 3 类核心规则（非空/唯一/枚举） | profiling 推荐、隔离表、自定义规则 |
| 表级血缘 | 列级血缘、影响分析 |
| 语义层 + 查询 + 2 种图表 | 看板联动、订阅、嵌入 |
| RBAC 三角色 + 审计 | 多租户配额、成本核算、OIDC |

**MVP 目标**：一条 ODS→DWD→DWS→ADS 链路能定时跑、能重跑、能看日志、能出一张图。这比「十个模块都半成品」有价值得多。

## 9. 推荐实施顺序（关键路径）

```
T0101 → T0104 → T0107 → T0102/T0103 → T0105/T0109   （地基，串行）
   ↓
T0201 → T0202 → T0204 → T0205 → T0206               （数据进得来）
   ↓
T0301 → T0302 → T0303 → T0305 → T0307               （模型立得住）
   ↓
T0401 → T0402 → T0404 → T0405 → T0406 → T0410       （管道跑得通）
   ↓
T0501 → T0503 → T0504 → T0505 → T0506 → T0507 → T0508（调度稳得住）
   ↓
T0701 → T0703 → T0704 → T0705                        （业务看得懂）
```

并行支线：
- `T0901/T0902` 可从 T0105 完成后启动，`T0905` 等 T0401/T0402 的 DSL 稳定后开工。
- `T0605/T0606` 可在 T0409 发布流程完成后插入，不阻塞主线。
- `T0801/T0802` 建议在 M4 之前完成，否则后期补权限会改动大量 handler。

## 10. 一句话原则

> **宁可少一个功能，不可多一条不可重跑的链路。**
> 数仓系统的价值不在功能数量，而在「每天跑出来的数是对的、错了能查、改了不炸」。
