# 引擎验证记录

本文件记录**在真实引擎实例上跑过什么、跑出了什么问题**，用来回答两个具体问题：

1. 「你说支持 MySQL/ClickHouse/DuckDB，是真跑过还是只写了方言？」
2. 「换一个引擎，DDL、写入、质量、指标这几条链路会不会悄悄坏掉？」

只记录实际执行过的用例。没跑过的能力一律写「未验证」，不写成「应该可以」。

## 1. 环境与结论

| 引擎 | 版本 | 接入方式 | 验证日期 | 结论 |
|---|---|---|---|---|
| PostgreSQL | 16-alpine | 容器，元数据库与业务库同实例 | 2026-11-14 | 全链路（含 demo 10 万行） |
| MySQL | 8.4 | 容器 | 2026-11-14 | 全链路（小数据量） |
| ClickHouse | 24.10.2.80 | 容器，HTTP 8123 | 2026-11-14 | 全链路（小数据量） |
| DuckDB | 1.1（驱动自带静态库） | 嵌入式文件，需 `-tags duckdb` | 2026-11-14 | 全链路（小数据量） |

统一用同一组模型/管道形态验证，避免「PG 上跑的是 A 场景、CH 上跑的是 B 场景」：

```
ODS 建表 → 灌数 → DWS 聚合（overwrite_partition）→ 重跑一次（验幂等）
        → 质量规则 4 条 → 指标查询（按天 + 按维度）→ 元数据采集 → 列级血缘
```

## 2. 逐引擎结果

### PostgreSQL 16

`make demo` 覆盖：10 万订单 / 2 万退款 / 1 万商品，7 天分区，三条管道 + 质量门禁 + 三张看板。
这是主链路，每次改动都会跑，结论见 `runner/PROGRESS.md`。

### DuckDB 1.1（`-tags duckdb`）

| 用例 | 结果 | 备注 |
|---|---|---|
| 建表 DDL（schema/主键/decimal） | 通过 | 见下方缺陷 5：此前连接器根本没编进二进制 |
| `overwrite_partition` | 通过 | 见下方缺陷 6：事务内删插同主键会被唯一索引拒绝 |
| `merge`（ON CONFLICT） | 通过 | 连跑两次行数不变 |
| 质量规则 | 通过 | 4 条规则全通过，分区收窄生效 |
| 指标查询 | 通过 | `DATE_TRUNC('day', dt)`，253.70 |
| 元数据采集 | 通过 | 见下方缺陷 7：`column_default` 为 NULL 导致整表采集失败 |
| 列级血缘 | 通过 | `ods_duck_order.amount → dws_duck_order_daily.gmv` |

DuckDB 是嵌入式单写锁：同一时刻只允许一个进程打开同一个 `.duckdb` 文件。
因此 CLI 与服务端不能同时读写同一文件——验证时全部通过服务端 API 完成，
这也是「同一数据源不要同时挂给两个 worker」的原因。

## 3. 这一轮真实执行暴露的缺陷

全部已修复，并补了回归用例。它们的共同点是：**只在真实引擎上执行才会暴露**，
单测和方言表检查都发现不了。

1. **ClickHouse 建库语句用错关键字**：DDL 编译对所有引擎都发 `CREATE SCHEMA IF NOT EXISTS`，
   CH 没有 SCHEMA 关键字，直接语法错误。改为按引擎发 `CREATE DATABASE`。
   → `internal/modelc/compile.go`、`TestCompileClickHouse`。
2. **ClickHouse 能力位写错**：连接器声明了 `InsertOverwrite`，实际 CH 没有这个语法
   （那是 Hive），分区覆写应走 `REPLACE PARTITION`。能力声明错一个，生成的就是跑不通的 SQL。
   → `clickhouse.Capabilities()`。
3. **临时表名拼接破坏标识符**：`` `dw`.`tbl` + "__tmp" `` 得到 `` `dw`.`tbl`__tmp ``，
   是语法错误。改为在引号内追加。
   → `internal/sqlx/write.go` `tmpName`、`TestTmpName`。
4. **文本协议的日期扫不进 time.Time**：CH 的日期是字符串，`assignScan` 只接受 `time.Time`，
   字符串被静默跳过，指标时间轴全变成 `0001-01-01`。改为按常见布局解析。
   → `internal/connector/memrows.go`、`TestAssignScanTimeFromString`。
5. **DuckDB 连接器从未被编进二进制**：三个 main 都只 import 了另外三个连接器，
   `-tags duckdb` 也因 go.mod 缺依赖而失败。用户看到的是「不支持的数据源类型」，
   而 stub 里精心写的提示永远不会出现。同时把 stub 的错误原样透出，
   而不是被包成笼统的「打开数据源失败」。
   → `cmd/*/main.go`、`connector.New`、`stub_test.go`。
6. **DuckDB 事务内删插同主键失败**：`DELETE` 后立刻 `INSERT` 相同主键，
   唯一索引在事务内不回收旧键，报 Duplicate key（官方 known index limitations）。
   改为两次提交并给出降级告警，牺牲原子性换取「重跑能成功」。
   → `PlanWrite`、`TestOverwritePartitionRerun`。
7. **DuckDB 元数据采集全军覆没**：`column_default` 为 NULL 时扫进 string 直接报错，
   每张表都被判失败，采集结果是 0 张表且只有一条 warn 日志。改用 `sql.NullString`。
   → `clickhouse/duckdb` 的 `DescribeTable`、`TestDescribeTableNullDefault`。
8. **DuckDB 的 DECIMAL 无法序列化/相加**：驱动返回 `duckdb.Decimal` 结构体，
   接口里 JSON 成了 `{"Width":18,...}`，指标查询扫 `*float64` 直接报类型转换错误。
   增加统一的行扫描层，把 DECIMAL 转成定点字符串。
   → `internal/connector/duckdb/scan.go`、`TestDecimalScan`、`TestDecimalIntoFloat`。
9. **MySQL 不建库导致写入报 1049**：DDL 编译把「MySQL 的 SCHEMA 等同 DATABASE」理解成
   「不必创建」，`schema: dws` 的模型只发 `CREATE TABLE \`dws\`.\`t\``。真实 MySQL 上
   建表与写入都报 `Error 1049 (42000): Unknown database 'dws'`，而 `Pool.Acquire` 是懒连接、
   不 Ping，所以数据源看起来是 `ok`，问题拖到管道执行才暴露。改为按引擎发
   `CREATE DATABASE IF NOT EXISTS`（本机 MySQL 9.x 实测：建库 → 建表 → upsert 落 2 行 →
   重跑幂等，全部通过）。注意已发布模型存的是 DDL 快照，修复后需重新发布（带「应用 DDL」）
   才会补上建库语句。→ `internal/modelc/compile.go`、`TestCompile`（`mysql 先建库` 子用例）。

## 4. 自动化现状

上述手动验证已经固化成可重复执行的用例：

```bash
make test-integration        # 起 postgres/mysql/clickhouse，跑 test/integration
SKIP_UP=1 make test-integration   # 依赖已在跑时跳过 docker compose
```

`test/integration/engine_test.go` 对每种引擎做同一件事：编译 DDL → 建表 → 插两行 →
`COUNT/SUM` → `DescribeTable` → 删表。DuckDB 用例带 `duckdb` 标签，走临时文件。

CI 里对应 `integration` job（`.github/workflows/ci.yml`），服务容器起 PG/MySQL/ClickHouse。
**注意**：该 job 只在本地用等价命令验证过，尚未在 GitHub Runner 上跑过一次。
