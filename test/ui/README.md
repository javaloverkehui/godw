# GoDW 控制台 UI 自动化

用真实浏览器点真实页面，然后回到元数据库里核对「刚才那一下到底写对了没有」。

一句话原则：**页面说成功不算成功，库里对得上才算。**

---

## 为什么要有这一层

后端单测能证明接口按约定返回，`test/integration` 能证明引擎能建表能查数，
但没人验证过下面这条链路：

> 用户点了「发布」→ 前端把 YAML 拼对了 → 接口收到的是这份 spec → 版本快照真的落库 →
> 刷新之后页面读的是新版本

这条链路上任何一环断了，单测和集成测试都是绿的，用户看到的是「发布了但没生效」。
`test/ui` 专门盯这一层，并且对每个写操作都配一条数据库断言。

## 快速开始

前置：控制台已在跑（默认 `http://127.0.0.1:8080`），元数据库可连（`godw/godw@127.0.0.1:5432/godw`）。

```bash
cd test/ui
npm install
npx playwright test                 # 全量，串行，约 1 分钟
npx playwright test tests/05-pipeline-instance.spec.ts
npx playwright test -g "TC-DS-03"   # 只跑一条用例
npx playwright show-report reports/html
```

用的是本机 Chrome（`channel: 'chrome'`），不额外下载浏览器。

环境变量（都有默认值，CI 上覆盖即可）：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `GODW_BASE_URL` | `http://127.0.0.1:8080` | 控制台地址 |
| `GODW_EMAIL` / `GODW_PASSWORD` | `admin@godw.local` / `admin12345` | 登录账号 |
| `GODW_DB_HOST` / `_PORT` / `_USER` / `_PASSWORD` / `_NAME` | `127.0.0.1` / `5432` / `godw` / `godw` / `godw` | 元数据库 |
| `GODW_E2E_RUN` | 时间戳 | 本轮数据前缀，用来隔离与清理 |

## 断言模型

每条用例至少两层，写操作三层：

1. **交互预期**：提示文案、弹窗开合、按钮状态、跳转、行数、空态。
   不写「元素存在」这种废话，写「用户看到什么、能不能继续操作」。
2. **数据预期**：拿 `pg` 直连元数据库，断言落库字段、版本号、级联删除、幂等。
3. **契约预期**（仅 `00-contract`）：脚本引用的 `data-act` 与表单 `id` 必须在当前前端产物里存在。

等待统一用「轮询到事实成立」（`waitForDb` / `expect.poll`），不用 `sleep`：
调度器认领实例、页面异步渲染都有先后，硬等既慢又脆。

## 怎么跟着 UI 改

前端是原生 JS，没有组件库，也没有 `data-testid`。这套脚本的稳定性靠三条约定：

1. **选择器只用 `data-act` / 表单 `id` / 可见文案**
   `data-act` 是事件委托的动作名，改样式、调布局都不会动它。
   所有选择器集中在 `src/pages.ts`，页面改版只改这一个文件。

2. **契约测试先红**
   有人重命名了动作或字段，`TC-CONTRACT-01` 会立刻失败，并直接列出：
   `前端已不存在这些动作，请更新 src/pages.ts：xxx`。
   不用等十几条业务用例集体报「元素找不到」。

3. **报错信息带业务语义**
   断言里写的是「第 3 行的状态」「规则 X 的总次数」，不是 `expect(true)`。
   挂了就能看出是数据错了还是页面错了。

新增用例的姿势：先在 `pages.ts` 加动作方法（只在这里写选择器），
再在对应 spec 里用业务语言串联，最后补一条数据库断言。

## 数据卫生

- 所有自建对象带 `e2e_<runId>` 前缀，spec 的 `afterAll` 按前缀清理。
- 只删自己建的；不碰真实数据源、模型、管道、分享。
- 例外：`audit_log` 是追加型审计，测试动作会留痕，**不清理**（清审计比留痕更糟）。
- `TC-DS-03` 会故意连一个不存在的端口，`TC-MODEL-02` 会故意用非法模型名——
  这些用例的价值就在于「失败路径不留脏数据」。

## 覆盖地图

| 页面 | 用例 | 深度 |
| --- | --- | --- |
| 登录 / 会话 | `01-auth` | 数据断言（令牌、账号） |
| 工作台 | `02-workbench` | 数据断言（计数、成功率、最近运行逐行） |
| 数据源 | `03-datasource` | 数据断言 + 失败路径不留脏数据 |
| 模型设计 | `04-model` | 数据断言（版本快照、级联删除） |
| 管道 / 运行实例 | `05-pipeline-instance` | 数据断言（实例、节点、重跑） |
| 自助查询 | `06-sql` | 数据断言（结果逐行、只读拦截） |
| 治理 / 分享 / 审计 | `07-governance` | 数据断言 + 匿名访问 |
| 质量 | `08-quality` | 数据断言（聚合与明细） |
| 数据文档 / BI 图表 | `10-catalog-bi` | 数据断言（字段清单、图表条数） |
| 全部 18 个路由 | `09-ux` | 冒烟 + 交互（主题、深链、搜索、遮罩） |
| 前端产物契约 | `00-contract` | 动作名与表单 id 的存在性 |

指标（`metrics`）、看板（`dashboards`）、血缘（`lineage`）、运维中心（`runbook`）、编排（`canvas`）
当前只做渲染冒烟——它们要么依赖画布像素坐标，要么依赖真实业务数据分布，
硬断言会变成「每次数据一变就红」的无效测试。需要时按同样模式补：先 page object，再交互 + DB 两层断言。

## 已知边界

- **dev 环境后端允许匿名（视为 admin）**：所以「未登录」状态用「本地放坏令牌 → `/me` 401」
  构造，这也正是令牌过期时用户的真实遭遇。
- 依赖真实调度器：`TC-PIPE-03/04/05` 触发的实例会被 worker 认领，用例会等它进入终态再断言。
- 用例串行（`workers: 1`）：共享同一套元数据与登录态，并行只会互相污染。
