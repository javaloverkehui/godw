性能与容量

实测环境：4 vCPU / 8 GB，PostgreSQL 16 与本服务同机，max_conns=20。 数据规模：ods.order 15 万行、30 个业务日期分区。

1. 读路径

godw-bench -c 10 -d 8s -s read 的实测结果：

指标 数值
总请求 59,935
吞吐 7,491 QPS
p50 1 ms
p90 1 ms
p99 61 ms
最大 76 ms
失败 9（压测结束瞬间的 context 取消，非服务错误）

压测覆盖三个接口：模型列表、实例列表、影响分析。99 分位 61 ms 主要来自影响分析的递归 CTE。

瓶颈判断

  • QPS 上不去的是数据库连接池，不是 HTTP 层。max_conns=20 时，10 并发已把池占满，再提并发只会增加排队。
  • 指标查询若命中缓存，p99 可降到 3 ms 以内；未命中时要扫 dws_order_daily 全表（30 天约 90 行，代价很低）。
  • 影响分析的递归深度每加 1 层约多 8–12 ms。depth=5 覆盖四层建模足够，不建议盲目调大。

2. 写路径

godw-bench -c 5 -d 10s -s write 打 POST /pipelines/{name}/run：

指标 数值
吞吐 约 120 实例/秒（创建，不等执行）
p99 210 ms

真正的执行吞吐由 worker 决定，单 worker 单实例约 200 ms（10 万行 ODS→DWD→DWS→ADS 全链路）。worker 数量是线性扩展的主要手段。

3. 容量规划

维度 单实例能力 扩展方式
并发任务 4（默认 --concurrency） 加 worker 副本
日调度任务 约 5 万（SKIP LOCKED 领取） 加 worker；元数据库升配
元数据表 千万级实例记录 instance 按 created_at 分区（见下）
血缘边 十万级 列级边按 workspace_id 分区

实例表增长

按每小时 100 个实例估算，一年约 87 万行，仍在单表舒适区。超过 500 万行时按周分区：

-- 示例：按周分区（需重建表，建议在维护窗口做）
CREATE TABLE instance_p2026w45 PARTITION OF instance
  FOR VALUES FROM ('2026-11-02') TO ('2026-11-09');

4. 关键参数

参数 默认 调优建议
db.max_conns 20 按 worker 数 × 4 + 20 估算；PG 侧 max_connections 要留余量
scheduler.lease_sec 90 小于最长节点耗时会导致误回收；大任务调到 300
scheduler.tick_sec 10 低于 5 秒收益递减，DB 压力上升
executor.max_rows 200000 超过这个行数的结果会被截断并记警告
semantic.cache_ttl_sec 60 报表类可到 300；要求实时则设 0

5. 已知性能债

  1. SELECT * 会让列级血缘缺失，不影响性能但影响治理质量。
  2. 看板一次请求串行取所有卡片。10 张卡片以上建议前端改成并发请求，或引入预聚合。
  3. 导出走全量内存。超过百万行应改为游标流式写 CSV（当前上限 5 分钟 / 由 MaxRows 兜底）。
  4. 指标查询没有下推分区裁剪。WHERE dt >= ... 依赖数据库自身的分区裁剪，PG 10+ 会自动做。

6. 复现实测

# 读
./bin/godw-bench -c 10 -d 30s -s read
# 写
./bin/godw-bench -c 5 -d 20s -s write
# 混合
./bin/godw-bench -c 20 -d 60s -s mixed

输出含 p50/p90/p99 与错误分布；有 5xx 时退出码为 1，可直接接进 CI。
