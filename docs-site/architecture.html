为什么控制面/数据面分离：调度与元数据是低频高一致性操作，SQL 执行是高频高资源占用操作。分离后可以只扩 worker、把 worker 放到数据所在网络、按资源组隔离（大查询不饿死小任务）。

2. 组件职责

组件 职责 不做什么
api 路由、参数校验、鉴权、审计埋点、SSE 不写业务逻辑，不直接碰 SQL
meta 元数据 CRUD、版本、发布、乐观锁 不执行 SQL
model 模型校验、逻辑→物理编译、DDL、schema diff 不连数据库执行
pipeline DSL 解析、DAG 校验、参数推导、节点编译 不调度
sqlx 模板渲染、宏、参数注入、方言函数、SQL 指纹 不决定何时跑
scheduler 到期生成实例、依赖判定、分发、租约回收 不执行任务
executor 领取任务、执行、心跳、上报结果与指标 不做依赖判断
quality 规则编译为 SQL、执行、判定、门禁 不修数据
lineage SQL 解析、血缘边、影响分析 不做可视化渲染
semantic 指标口径、查询构建、RLS 注入、缓存 不存明细数据
bi 图表/看板配置、导出、订阅 不做数据加工
auth 认证、RBAC、脱敏策略 不写业务规则

3. 技术选型

领域 选型 理由
语言 Go 1.22+ 单二进制、并发模型适合调度、部署简单
HTTP Gin 1.10 生态成熟、中间件丰富、上手快
配置 Viper（yaml + env 覆盖） 多环境配置简单
元数据库 PostgreSQL 16 JSONB 存 DSL、SKIP LOCKED 直接当队列、分区表存实例
数据访问 pgx/v5 + sqlc 类型安全、SQL 显式可控，避免 ORM 魔法
迁移 goose 纯 SQL 迁移，可回滚，CI 友好
缓存/锁 Redis 7（可选） 查询结果缓存、分布式锁；单机模式可关闭
调度 自研（PG 队列 + 租约） 避免引入 Temporal 的运维成本；万级日任务足够
SQL 解析 pingcap/tidb/parser 支持 MySQL 方言子集，列级血缘可用
前端 React 18 + TS + Vite 主流、组件生态好
UI Ant Design 5 后台系统开箱即用
DAG 画布 AntV X6 节点/连线/锚点/自动布局能力强于 ReactFlow
图表 ECharts 5 国内图表需求覆盖最全
编辑器 Monaco SQL 高亮、补全、diff
状态 Zustand + TanStack Query 轻量，服务端状态与 UI 状态分离
鉴权 JWT + Casbin RBAC 模型可配置
可观测 zap + Prometheus + OTel 日志/指标/链路三件套
部署 Docker Compose（单机）/ Helm（K8s） 先能跑起来，再谈弹性

4. 核心数据流

4.1 定义期（Design Time）

YAML/UI 输入
   │
   ├─ 模型：校验 → 编译 DDL → 存 model + model_version（不可变快照）
   ├─ 管道：校验 DAG → 解析 ref() 依赖 → 存 pipeline + pipeline_version
   └─ 指标：绑定 dataset + 表达式 → 存 metric

关键约束：published 版本不可变。运行中的实例永远绑定某个 version_id，改定义不影响正在跑的任务。

4.2 运行期（Run Time）

cron 到期
  → 生成 task_instance（唯一键 pipeline+node+bizdate，重复则忽略）
  → 依赖解析：上游全 SUCCESS → READY
  → 分发：资源组有空位 → QUEUED
  → worker 租约领取 → RUNNING（lease_until = now + timeout）
  → 心跳续租 / 崩溃后回收重派
  → 执行：渲染 SQL（快照）→ 连接器执行 → 写审计列 → 上报
  → SUCCESS/FAILED → 唤醒下游 → 指标/告警/质量

4.3 服务期（Serving）

BI 请求 {dataset, dimensions, measures, filters}
  → 权限校验 + RLS 条件注入
  → 查询构建器生成 SQL（带 LIMIT / 时间粒度 / 方言函数）
  → 缓存命中? 返回 : 执行 → 缓存 → 返回列元数据 + 行数据

5. 部署拓扑

单机版（开发/小团队）：godw-server 单进程内含调度器与内嵌 worker，外接一个 PostgreSQL，DuckDB 可作为本地计算引擎。

标准版（生产）：

            ┌────────────┐
   LB  ────▶│ godw-server │ × 2（无状态，仅一个实例持有调度锁）
            └─────┬──────┘
                  │
            ┌─────▼──────┐        ┌──────────────┐
            │ PostgreSQL │        │ MinIO / OSS  │
            └─────┬──────┘        └──────▲───────┘
                  │                      │
       ┌──────────▼──────────┐           │
       │  godw-worker × N    │───────────┘
       │  按资源组打标签      │

  • worker 按 resource_group 打标签（etl / bi / heavy），任务按组路由。

6. 关键设计决策（ADR 摘要）

编号 决策 备选 取舍理由
ADR-01 调度队列用 PostgreSQL SKIP LOCKED Kafka / Redis / Temporal 少一个中间件；事务内改状态天然一致；万级/日完全够用
ADR-02 元数据用 sqlc 而非 GORM GORM / ent 复杂查询（血缘递归、实例分页）用 SQL 更清晰，性能可预期
ADR-03 连接器编译期注册而非 Go plugin plugin 包 Go plugin 版本/ABI 地狱，编译期注册 + 接口稳定更可靠
ADR-04 管道 DSL 用 YAML 而非纯画布 JSON 画布直存 YAML 可 review、可 diff、可被 AI 生成；画布是它的可视化视图
ADR-05 渲染快照落库 重跑时重渲染 防止上游模型变更导致重跑结果不一致，满足审计
ADR-06 列级血缘用 AST 解析而非日志推断 查询日志反解 定义期即可得血缘，不必等任务跑过；准确率更高
ADR-07 前端 DAG 用 X6 而非 ReactFlow ReactFlow 锚点、正交路由、群组、自动布局更适合数据管道

7. 非功能指标

指标 目标
元数据 API p95 ≤ 200ms（10 万表规模）
调度吞吐 ≥ 500 实例/分钟（单调度器）
worker 单实例并发 32 个 SQL 任务（可配）
任务状态可见延迟 ≤ 2s（前端轮询/SSE）
日志首行延迟 ≤ 1s（SSE 推送）
DAG 画布 500 节点拖拽 ≥ 40fps
崩溃恢复 worker 被杀后 ≤ 60s 自动重派
单表元数据采集 1000 表 ≤ 30s
