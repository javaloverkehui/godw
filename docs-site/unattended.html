05 · 无人值守执行方案

需求：100 张任务卡要连续跑完；App 可能退到后台、沙箱可能休眠、进程可能随时被杀；中断不能导致任务停摆或重复劳动。

1. 先说结论

执行任务的模型本身无法在自己被杀死后继续运行。 所以真正的解法不是「让进程不死」，而是：

把「什么时候继续干」交给沙箱之外的调度器；把「干到哪了」写进磁盘上的状态机。

任何时刻被杀，最多损失当前这一张卡未提交的改动；下一次唤醒自动从断点继续，不会重头再来，也不会重复已完成的任务。

2. 三种方案对比

方案 调度在哪 需要 App 常开 断点续跑 适用
A. 平台定时任务（推荐） 云端 否 是 没有常开机器，想最快跑起来
B. 自有机器 cron + agent CLI 你的 Mac/服务器 否 是 有常开机器，要求最稳、可改调度
C. 人工分段推进 你 是 是 关键节点需要人判断，或任务本身要讨论

三者可以混用：A 跑日常，B 做兜底，C 在里程碑验收。

3. 核心机制：状态机 + 单任务提交 + 互斥锁

        ┌────────── next ──────────┐
        ▼                          │
    pending ──▶ running ──▶ done ──┘（依赖满足后解锁下游）
        ▲           │
        │           ├── fail（<3 次）──▶ pending
        │           ├── fail（≥3 次）──▶ blocked（跳过，不阻塞无关任务）
        │           └── handoff（时间到）─▶ pending（保留笔记）
        └──────── reset（人工修复后）

四条保证：

  1. 单任务提交：一次只做一张卡，做完立即 git commit。半成品不会污染主分支太久。
  2. 互斥锁：runner/.locks/<worker>.lock 记录 task/pid/开始时间；同一个 worker 重叠唤醒直接退出。
  3. 陈旧锁接管：锁超过 90 分钟视为进程已死，下一次唤醒自动接管并把该任务退回 pending。
  4. 失败升级：同一张卡失败/交接 3 次 → blocked，继续做别的；依赖它的任务自动跳过，最后集中处理。

4. 已经搭好的东西

runner/
├── build_tasks.py      从 docs/tasks/*.md 解析任务 + 手工校准的依赖表 → tasks.json
├── tasks.json          100 个任务：id/标题/优先级/人日/依赖/文件范围(scope)/层级
├── tick.py             状态机：next / done / fail / handoff / plan / report
├── state.json          唯一真相：每卡状态、尝试次数、备注、commit、worker
├── CURRENT.md          当前任务说明（单 worker）
├── PROGRESS.md         人读进度板
├── PROMPT.txt          单 worker 的定时任务提示词
├── PROMPT-worker.txt   多 worker 提示词模板（替换 {WORKER}）
├── .locks/             每个 worker 一把锁（运行时生成）
└── .state.lock         状态文件读写锁（防止并发写坏）

任务清单不是手写的：build_tasks.py 从五份任务卡 Markdown 解析生成，改了卡片重新跑一次即可。当前结果：100 个任务、191 人日。

依赖不是「同 Epic 顺延」，而是手工校准的硬依赖：只有「不做 A 就没法做 B」才连边。效果：

  • 关键路径 41 人日（原来串行是 191 人日）
  • 最大可并行宽度 9（第 14 层）
  • 可立即开工的任务 1 个（T0101），之后迅速展开

5. 一轮（tick）的完整流程

cd /workspace/数据仓库

# ① 领任务（拿锁、写 CURRENT.md、打印提示词）
python3 runner/tick.py next --budget 45

# ② 执行：读 CURRENT.md，按任务卡实现、写测试、跑测试
#    完成后提交
git add -A && git commit -m "feat(T0101): 仓库骨架"

# ③ 收尾（三选一）
python3 runner/tick.py done    --note "实现并通过 go test ./..."
python3 runner/tick.py fail    --note "编译错误 xxx，已尝试 yyy"
python3 runner/tick.py handoff --note "完成 A；未完成 B；下一步 C"

next 做了五件事：检查锁 → 选出依赖已满足且不与在跑任务冲突的任务 → 尝试次数 +1 → 生成 CURRENT.md（含任务卡原文、必读文档、上一次的失败笔记）→ 打印本轮提示词。

关键设计：失败信息会写进下一次的 CURRENT.md。 模型上下文每次都是新的，但「上次为什么失败」不会丢。

5.1 并行执行：多 worker + 独立 worktree

单 worker 是一条流水线；要提高吞吐就开 2–3 个 worker，每个 worker 有独立的 git worktree 和分支，互不干扰。

# 看依赖分层与「哪几个任务可以同时开工」
python3 runner/tick.py plan

# 三个 worker 各自领任务（会自动错开同目录的任务）
python3 runner/tick.py next --worker w1 --budget 45
python3 runner/tick.py next --worker w2 --budget 45
python3 runner/tick.py next --worker w3 --budget 45

领到任务后会打印工作目录，例如：

【T0305】跨引擎类型映射矩阵
worker w2　预算 45 分钟
工作目录：/workspace/.godw-worktrees/w2（分支 task/T0305-w2）

Agent 进入该目录写代码、commit，然后回到主仓库执行：

python3 /workspace/数据仓库/runner/tick.py done --worker w2 --note "..."

done 会做四件事：检查 worktree 是否干净 → go build ./... 预检 → 串行合并回主分支 → 删除 worktree。

冲突如何避免（三道）：

机制 说明
依赖 硬依赖未完成，不进入候选
文件范围（scope） 从任务卡「产出」自动提取目录；两个任务目录重叠则不并发，另一个 worker 会跳过它
范围未知 产出里没有路径的任务视为「与所有任务冲突」，只能单独跑（宁可慢，不可撞）

限制：合并是串行的（.merge.lock），并行收益主要在「写代码 + 跑测试」阶段；合并阶段会短暂排队。合并冲突会直接标 blocked 并保留分支，人工处理。

5.2 开几个 worker 合适

worker 数 适用 说明
1 刚起步、T0101 还没做完 前 2 层任务几乎都依赖基座，并行意义不大
2 稳妥提速 一个做后端主线，一个做前端/治理支线
3 推荐上限 再多会因为合并排队与 scope 冲突互相等待
>3 不建议 上下文切换与合并冲突的收益递减

6. 方案 A：平台定时任务（推荐）

在 App 的「自动化 / 定时任务」里建任务。单 worker 建 1 个；并行建 3 个，{WORKER} 分别填 w1/w2/w3。

配置项 建议值
频率 每 30 分钟
单次超时 60 分钟（必须 ≥ 预算 + 15 分钟）
执行环境 云端（与 App 是否打开无关）
提示词 runner/PROMPT-worker.txt，替换 {WORKER}

单 worker 提示词（runner/PROMPT.txt，直接复制）：

你是 GoDW 项目的自动执行工程师。本轮严格按步骤执行，不要做额外的事：

1. 运行：cd /workspace/数据仓库 && python3 runner/tick.py next --budget 45
2. 如果输出「已有任务在跑」或「全部完成」，立即结束本轮，不要修改任何文件。
3. 否则读取 runner/CURRENT.md，按其中的任务卡完成实现。
4. 只改与该任务相关的文件；必须运行相关测试；通过后 git commit。
5. 最后必须执行 tick.py done / fail / handoff 之一（命令在 CURRENT.md 末尾）。
禁止修改 runner/state.json 与 runner/tasks.json。

多 worker 提示词（{WORKER} 替换为 w1/w2/w3）：

你是 GoDW 项目的自动执行工程师，代号 {WORKER}。本轮严格按步骤执行：

1. 运行：cd /workspace/数据仓库 && python3 runner/tick.py next --worker {WORKER} --budget 45
2. 如果输出「没有可领取的任务」或「全部完成」，立即结束本轮。
3. cd 到输出的 worktree 目录（在 {WORKER} 自己的 CURRENT.md 里），按任务卡实现。
4. 只改与该任务相关的文件；必须运行相关测试；通过后在该 worktree 里 git commit。
5. 回到主仓库执行：python3 /workspace/数据仓库/runner/tick.py done --worker {WORKER} --note "..."
   失败/超时用 fail / handoff，同样带 --worker {WORKER}。
禁止在主仓库直接改代码；禁止修改 runner/state.json 与 runner/tasks.json。

为什么是 30 分钟一次：任务提前完成时下一轮会空跑（几秒退出，成本可忽略）；任务超时则由 handoff 保住进度。同一个 worker 的重复唤醒会被锁挡住；不同 worker 会被 scope 冲突规则错开。

如果平台单次最长只能跑 20 分钟，把 --budget 降到 15、超时设 20，用更高频率补偿。

7. 方案 B：自有机器 cron（最稳）

适合你有常开的 Mac mini / 云主机，且项目代码在本地（不依赖沙箱）。

# crontab -e
*/30 * * * * cd /Users/kenny/work/godw && \
  /path/to/agent-cli --headless -p "$(cat runner/PROMPT.txt)" \
  >> runner/logs/cron.log 2>&1

要点： - PROMPT.txt 就是第 6 节那段提示词（固定不变）。 - 用 flock 包一层防重入：flock -n runner/.cronlock ...。 - 日志按天切分，失败时把最后 50 行发到告警渠道。 - 如果部署在服务器，建议用 systemd timer 替代 cron，能看到失败状态与重试记录。

8. 中断语义（最重要的部分）

中断时机 结果 恢复方式
next 刚跑完，还没动代码 任务停在 running，锁未过期 等 90 分钟后自动接管，或删 runner/.locks/<worker>.lock 后立即 next
改了一半代码，未 commit 工作区有未提交改动，任务 running 下一次 next 接管后，CURRENT.md 会附上「上次尝试」笔记；模型先看 git status 再决定复用还是丢弃
已 commit，未 done 代码已保存，状态仍 running 接管后重跑测试，通过则 done
done 后被杀 状态已落盘，进度已 +1 无影响，下一轮领新任务
fail 后达上限 标记 blocked 人工修复后 reset <ID> 重新入队

唯一可能丢的是「未 commit 的当前任务改动」，最多一张卡的工作量。这也是要求「每完成一个可工作阶段就保存」的原因。

8.1 如果沙箱被重建

上面的方案默认「同一个工作区在两次唤醒之间保留」。如果平台的定时任务每次给你一个全新沙箱，就再加一层保险：

  1. 代码推到远端：done 之后除了 commit，再 git push（失败不阻塞，下一轮重试）。
  2. 进度跟着代码走：runner/state.json 与 runner/tasks.json 一起提交，不要写进 .gitignore。
  3. 唤醒时自愈：提示词里加一句「若 /workspace/数据仓库 不存在，先 git clone <repo> 再继续」。
  4. 克隆后 tick.py next 会读到 state.json，从中断处继续，而不是从 T0101 重来。

这样即使沙箱是全新的，最坏情况也只是重跑当前那一张卡。

9. 质量闸门（防止跑得越快错得越远）

  1. 每卡必测：CURRENT.md 明确要求跑 go build ./... 与相关 go test，不通过不许 done。
  2. 每卡必提交：commit message 带任务 ID，出问题可精确回滚到任意一张卡。
  3. 三个人工检查点（各 30 分钟）： - M3 后（T0307 完成）：看模型编译与分层约束是否符合预期，此时纠正成本最低。 - M5 后（T0512 完成）：跑一次真实的「调度→失败→重试→补数」，确认可靠性。 - M7 后（T0710 完成）：打开看板看数，确认端到端可用。
  4. 每 20 张卡看一次 PROGRESS.md：若 blocked 超过 5 个，停下来人工处理，不要让自动化空转。

10. 节奏预估

指标 单 worker 3 worker
任务数 100 100
单轮预算 45 分钟 45 分钟
平均每卡轮次 1.5–2.5 轮 1.5–2.5 轮
总轮次 150–220 160–240（含冲突重排）
机器时间 3–5 天 2–3 天
叠加失败重试与人工检查点 实际 2–3 周 实际 1.5–2 周

并行不是线性加速：合并要排队，scope 冲突会让某些 worker 空转，复杂卡依然会连续占用同一个 worker。3 个 worker 的实测收益通常在 1.5 倍左右，不是 3 倍。

不要期待「一夜跑完 191 人日」——AI 写代码快，但验证慢，而且任务卡之间的一致性需要检查点兜底。

11. 这套方案不能保证什么

  • 不能保证一次写对：复杂卡（T0406 写入策略、T0607 列级血缘、T0905 画布）大概率要 2–3 轮。
  • 不能保证风格统一：上下文每次重置，只能靠 docs/03 的契约与 CURRENT.md 的必读清单约束。
  • 不能保证依赖判断最优：依赖是手工校准的，scope 是从「产出」路径推断的；跨模块重构仍可能撞车，撞了会标 blocked 保留分支，需要人工合。
  • 平台配额与超时是硬约束：单轮超时若小于预算，任务会被腰斩，只能降预算、提频率。
  • 并行会放大不一致：两个 worker 同时引入同一套工具的不同用法，合并后需要一次统一（检查点时做）。

12. 现在就能开始

cd /workspace/数据仓库
python3 runner/tick.py status              # 100 pending
python3 runner/tick.py plan                # 看关键路径与并行分层
python3 runner/tick.py next                # 单 worker：领 T0101
python3 runner/tick.py next --worker w1    # 多 worker：各领各的

然后把第 6 节的提示词贴进定时任务，频率 30 分钟。之后你只需要偶尔看一眼 runner/PROGRESS.md。
