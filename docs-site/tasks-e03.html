E03 分层建模（16 人日）

T0301 · 模型 DSL 与校验 P0 2d

目标：用一份 YAML 描述一张数仓表，且能被人和 AI 读懂。 要点 - 结构体对齐 docs/03 第 4 节 ModelSpec；同时输出 schema/model.schema.json（JSON Schema Draft 2020-12）供编辑器补全。 - 校验分三层：语法（JSON Schema）→ 语义（层规则、主键、分区字段存在）→ 环境（目标数据源是否支持该类型/物化方式）。 - 错误必须结构化：{path: "columns[3].type", code: "invalid_type", message: "decimal(18,4) 在 clickhouse 需指定精度"}，前端可直接定位到表单字段。 - 支持 godw validate -f model.yaml 离线校验。 产出：internal/pipeline/dsl/model.go、schema/*.json、校验器与 30 个反例测试。 验收：30 个反例全部报出正确 path；合法样例零告警；JSON Schema 能在 VSCode 中生效。

T0302 · 模型编译器（逻辑 → DDL） P0 3d

目标：一份模型定义，编译出四种引擎都能跑的建表语句。 要点 - Compile 必须是纯函数（无 IO、无全局状态、无时间依赖），便于表驱动测试与快照对比。 - 输出按引擎组织语句序列：PG/MySQL 单条 CREATE TABLE；CH 需 CREATE TABLE ... ENGINE = MergeTree() PARTITION BY ... ORDER BY ... TTL ...；Doris 需 DISTRIBUTED BY HASH(...) BUCKETS n。 - 列注释：PG 用 COMMENT ON COLUMN，MySQL 内联 COMMENT，CH 用 COMMENT 子句，Doris 内联。 - 生成 CREATE TABLE IF NOT EXISTS 与「已存在则比对」两套路径；结构不一致时报 schema drift，不静默跳过。 - DDL 输出稳定排序（列按定义顺序、选项按固定键序），保证 diff 可比。 产出：internal/modelc/compile.go、ddl_{pg,mysql,ch,doris}.go、golden 测试。 验收：同一模型四引擎 DDL 快照测试通过；两次编译字节级一致；对已存在且结构不同的表返回明确错误码。

T0303 · 分层规范强制 P0 1.5d

目标：让「分层」成为约束而非口号。 要点 - 表名必须匹配 ^(ods|dwd|dws|ads)_[a-z][a-z0-9_]*$，否则编译失败。 - 引用规则：ods 只能引用数据源原始表；dwd 引用 ods/dwd；dws 引用 dwd/dws；ads 引用 dwd/dws/ads。跨层引用（如 ods 直接读 dws）一律拒绝。 - 每层必填列：dt DATE；ODS 额外 _godw_src STRING、_godw_load_at TIMESTAMP；DWD/DWS 必须有主键或粒度声明。 - 规则以配置表实现（layer_rule），允许工作空间级覆盖，但默认值不可关闭「禁止反向依赖」。 产出：internal/modelc/rules.go、规则配置与测试。 验收：构造 12 种违规引用，全部被拒且错误信息说明「哪条规则、哪个字段」。

T0304 · 分区、分桶与生命周期 P0 1.5d

目标：控制存储成本与查询效率。 要点 - storage.partitionBy 支持表达式（dt、toYYYYMM(dt)、date_trunc('month', dt)），编译时按引擎能力转换。 - ttl 支持 30d/12m/3y，转成 CH TTL dt + INTERVAL、PG 分区删除策略（由维护任务执行）。 - 分区字段必须在列定义中存在且非空；分区粒度不得细于小时（防小文件）。 - 提供「分区预创建」能力：维护任务提前 7 天建分区。 产出：modelc/partition.go、维护任务、TTL 清理逻辑。 验收：CH 建表后 system.parts 分区符合预期；过期分区在维护任务执行后被删除并留审计。

T0305 · 跨引擎类型映射矩阵 P0 2d

目标：一处定义类型，处处可用。 要点 - 逻辑类型集合：string,text,int32,int64,float64,decimal(p,s),bool,date,timestamp,json,array<T>,map<K,V>。 - 维护矩阵（Go 表 + 文档表格双份，测试保证一致）：行=逻辑类型，列=引擎，值=物理类型 + 是否需精度参数 + 是否有损。 - 有损映射（如 json → string、decimal(38,10) → decimal(18,4)）编译时产生 warning，需显式 allowLossy: true 才放行。 - 反向映射（引擎类型 → 逻辑类型）用于元数据采集与 ODS 自动建模。 产出：dialect/types_matrix.go、docs/type-matrix.md、双向转换测试。 验收：矩阵每个单元格都有测试；有损转换未声明时编译失败。

T0306 · Schema 变更管理 P0 2d

目标：改表结构不能悄悄搞坏下游。 要点 - Diff(old, new) 输出 Change{Kind, Column, From, To, Breaking}；判定规则：删列/改类型/改分区/改主键 = breaking；加可空列/加注释 = safe。 - breaking 变更必须走「申请 → 影响分析（调 T0609）→ 审批 → 执行」流程；MVP 可先用「二次确认 + 记录操作人」。 - 提供迁移 SQL 生成：ALTER TABLE ... ADD COLUMN，CH 的 ADD COLUMN 需带 AFTER；不支持的类型变更给出「新建表 + 双写 + 切换」建议。 - 所有变更写 model_version 与审计日志，可回滚到任意历史版本。 产出：modelc/diff.go、变更申请 API、迁移 SQL 生成器。 验收：删列被判定 breaking 并拦截直接发布；加列生成正确 ALTER；回滚后 DDL 与历史版本一致。

T0307 · 版本与发布 P0 1.5d

目标：定义可追溯，运行不受编辑影响。 要点 - publish 生成不可变 model_version 快照（含 DDL 与 hash），version 自增；draft 可随意改。 - 运行中的任务绑定 version_id；发布新版本不改变已排队实例的行为。 - rollback(model, version) 生成新版本（内容等于旧版），不删除历史，保证审计链完整。 - 同名模型并发发布用 SELECT ... FOR UPDATE 或唯一约束兜底。 产出：internal/meta/service/model_publish.go。 验收：发布后修改 draft 不影响已发布版本；回滚产生 version+1 且 ddl_hash 与目标版本相同。

T0308 · 物化方式 P1 1.5d

目标：支持不同时效与成本要求。 要点 - table：物理表，调度写入；view：逻辑视图，不占存储，查询实时；mv：物化视图（CH/PG 支持，MySQL 不支持需降级为表+定时刷新）；incremental：增量表，配合写入策略。 - 不支持时编译期报错并给替代方案，不允许静默降级。 - view 不允许配置 TTL/分区，校验时拒绝。 产出：modelc/materialization.go。 验收：MySQL 上定义 mv 返回明确错误与建议；view 的查询能正确透传到底表。

T0309 · 建模脚手架 P1 1d

目标：降低建表门槛，保证新表天然合规。 要点 - godw init model --layer dwd --from ods_order --name dwd_order_detail 读取源表结构，自动生成 YAML 骨架（含 dt、审计列、注释、类型映射）。 - 生成时自动推断主键候选（唯一且非空的列）并提示确认。 - 模板内置四层各一套标准字段（ODS 审计列、DWD 主键区、DWS 粒度区、ADS 展示区）。 产出：internal/cli/init_model.go、模板文件。 验收：从 MySQL 表生成 YAML 后 godw validate 直接通过；字段顺序与源表一致。

T0310 · 数据字典与注释同步 P2 1d

目标：文档跟着模型走，不靠人肉维护。 要点 - 发布时把列注释写入引擎（COMMENT ON / 内联），并从引擎回读校验。 - godw export-doc --format md|html 输出数据字典：表清单、字段、类型、口径说明、上下游。 - 字典页支持按层/标签筛选，可导出 Excel。 产出：internal/modelc/doc.go、导出命令。 验收：修改注释并发布后，引擎中 col_description 同步更新；导出的 md 表格列齐全。

E04 管道与 SQL 引擎（20 人日）

T0401 · 管道 DSL 与存储 P0 2d

目标：管道可读、可 diff、可被 AI 生成。 要点 - 结构对齐 docs/03 第 5 节；nodes[].key 全局唯一，type 必须在注册表中。 - YAML ↔ JSON 双向往返无损（前端画布用 JSON，CLI 用 YAML）。 - 保存草稿时只做语法校验；publish 时做全量校验并编译。 - 图数据同时写 pipeline_node/edge（便于反查）与 pipeline_version.graph（运行快照）。 产出：internal/pipeline/dsl/*、schema/pipeline.schema.json。 验收：YAML→JSON→YAML 往返一致；重复 key 报错定位到行号。

T0402 · DAG 校验 P0 2d

目标：发布前拦住所有图结构错误。 要点 - 校验项：环检测（Kahn 拓扑排序）、孤立节点（无入边且非 source）、悬空依赖、dependsOn 与 edges 不一致、节点 key 重复、必填字段缺失。 - 端口类型校验：source 无入边；quality 必须有入边；branch 必须有 then/else。 - 输出结构化错误列表（可一次返回多个），前端在画布上高亮对应节点。 - 拓扑序计算结果缓存进 compiled，调度时直接用。 产出：internal/pipeline/compile/dag.go、validate.go。 验收：构造 10 种坏图全部被拒且错误指向正确节点；1 万节点图校验 ≤ 200ms。

T0403 · 参数系统 P0 2d

目标：同一条管道跑不同日期、不同区域，不复制粘贴。 要点 - 四类命名空间（sys/p/g/nodes）与优先级：节点参数 > 管道参数 > 全局变量 > 系统默认。 - 日期运算在渲染期完成：${sys.bizdate-1d}、${sys.bizdate-7d}、${sys.month_start}；统一 yyyyMMdd，输出到 SQL 时按列类型加引号。 - 类型系统：string/int/bool/date/enum，触发时校验并转换；缺必填参数直接拒绝触发。 - params_snapshot 落库；重跑默认复用快照。 产出：internal/pipeline/params/*、解析器与 20 个用例。 验收：${sys.bizdate-1d} 在月末/年初跨月跨年正确；非法枚举值返回 400 并列出可选值。

T0404 · SQL 模板引擎 P0 3d

目标：写得像 dbt，但比 dbt 更可控。 要点 - 两阶段渲染：先解析 {{ }} 函数（ref/src/macro/mask/var），再替换 ${ } 变量；顺序不可颠倒。 - ref() 副作用：注册表依赖 + 生成血缘边 + 校验模型存在且已发布；未发布时报错而不是静默用草稿。 - 宏库内置：partition_range(days)、date_spine(start,end)、dedup(keys,order)、surrogate_key(cols)；宏用 Go 函数实现，禁止用户自定义任意代码。 - 渲染结果与 refs 列表一起返回；同一输入必须字节级一致（禁止 map 遍历顺序影响输出）。 - 提供 godw render --node clean --bizdate 20251110 命令行预览。 产出：internal/sqlx/{render,funcs,macros}.go。 验收：ref() 拼错表名报 model not found: xxx；渲染 1000 次结果 hash 一致；宏参数非法时报具体宏名。

T0405 · 方言抽象层 P0 2.5d

目标：一套 SQL 逻辑，四种引擎都能跑。 要点 - 实现 Dialect 接口全部方法；标识符转义、占位符、分页、日期截断、日期加减、字符串拼接、空值处理、正则、JSON 取值逐项覆盖。 - 函数映射表：逻辑函数名 → 各引擎实际函数；未覆盖时编译期报 unsupported function 并指出引擎。 - 能力矩阵 Capability 与方言解耦：方言管语法，能力管特性（是否有 MERGE、是否支持窗口）。 - 单测方式：同一逻辑 SQL 在四引擎执行，结果集必须一致（用 testcontainers）。 产出：internal/dialect/{postgres,mysql,clickhouse,doris,duckdb}/*、一致性测试。 验收：20 条跨引擎 SQL 结果一致；date_trunc('week') 在 CH 与 PG 周起始一致（周一）。

T0406 · 六种写入策略 P0 3d

目标：写入必须幂等，重跑不产生重复数据。 要点 - 实现 append / overwrite_partition / merge / scd2 / full_refresh / delete_insert，按 Capability 选择实现路径。 - merge：优先原生 MERGE；PG 用 ON CONFLICT DO UPDATE；MySQL 用 ON DUPLICATE KEY UPDATE；CH 用 ReplacingMergeTree + FINAL 或 ALTER TABLE ... UPDATE（明确写选型理由）。 - scd2：先 UPDATE 关链（end_date= bizdate, is_current=0），再 INSERT 新版本；必须在事务内，无事务引擎拒绝执行。 - overwrite_partition：能力优先级 INSERT OVERWRITE（Doris）→ ALTER TABLE ... REPLACE PARTITION（ClickHouse，需先写临时表）→ DELETE + INSERT（PG/MySQL，必须包在事务里）。三档都不支持时返回 ErrUnsupported，不允许静默全量覆盖。 - 所有写入自动补 _godw_run_id、_godw_bizdate、_godw_load_at（若模型声明）。 - 生成语句序列 []string，由执行器顺序执行并记录每条耗时。 产出：internal/sqlx/write.go、各策略实现、golden 测试。 验收：6 策略 × 4 引擎快照测试；每策略连跑两次，目标表行数与内容不变；scd2 二次运行后历史版本数正确。

T0407 · 增量条件推导 P0 2d

目标：不写 WHERE 也能只跑增量。 要点 - 依据模型 storage.partitionBy 与 bizDate 自动注入分区裁剪条件（dt = '20251110'）。 - 若源表无分区字段，降级为时间列推导（updated_at >= bizdate AND < bizdate+1），并在编译结果中标注 inference: time_column。 - 无法推导时不猜：显式报错要求手写 where，避免全表扫描。 - 推导逻辑输出到 compiled.inference 供前端展示「本次将扫描的分区」。 产出：internal/pipeline/compile/incremental.go。 验收：无分区字段的源表触发明确报错；推导结果与实际扫描分区一致（用 CH system.query_log 校验）。

T0408 · 内置算子 P1 3d

目标：常见清洗不用手写 SQL。 要点 - 算子：dedup(keys, orderBy)、cast(map)、rename(map)、filter(expr)、join(model, on, type)、union(models)、aggregate(groupBy, aggs)、window(partitionBy, orderBy, fn)、mask(columns, strategy)。 - 算子编译为 SQL 片段，最终仍走 sqlx 渲染；不允许算子内部直接执行。 - 每个算子有 JSON Schema 描述参数，前端据此生成表单。 - 算子组合顺序即 SQL 嵌套顺序，输出带注释标明来源算子，便于排查。 产出：internal/pipeline/node/operators/*。 验收：每个算子有「输入样例 → 输出 SQL」快照；mask 对 high 级 PII 必须生效。

T0409 · 版本、发布与灰度 P0 1.5d

目标：改管道不影响线上。 要点 - draft 可编辑；publish 生成不可变 pipeline_version；调度只认 published。 - 生产环境发布需二次确认（前端输入管道名）；支持「只发布不调度」用于灰度。 - 运行中实例保留旧 version_id；新实例用新版本。 - 提供版本对比 API：返回 graph diff（新增/删除/修改节点与连线）。 产出：service/pipeline_publish.go、diff API。 验收：发布新版本后，进行中的实例仍用旧版本执行；diff 能准确列出改动节点。

T0410 · 试跑与 Dry-run P0 2d

目标：上线前能看到「将要执行什么」。 要点 - dry-run：完整渲染 SQL + 参数 + 目标表 + 预计扫描分区，不连库执行；返回每条语句与 refs。 - sample-run：对 SELECT 部分包一层 LIMIT 100 真跑，返回列与样例数据，用于验证字段与类型。 - 试跑结果不写目标表（事务回滚或只跑 SELECT）。 - 前端展示「渲染后 SQL」并支持复制、格式化、与上次对比。 产出：service/pipeline_dryrun.go、sample-run 执行器。 验收：dry-run 不产生任何写入（查 run 表无记录）；sample-run 返回 ≤100 行且列类型正确。
