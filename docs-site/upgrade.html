升级与兼容

1. 版本策略

MAJOR.MINOR.PATCH：

变更 版本位 是否破坏兼容
新增表、新增可空列、新增接口、新增字段 MINOR 否
删除列、改列类型、改接口语义、改 YAML 必填项 MAJOR 是
修 bug、优化性能 PATCH 否

当前 0.x 阶段：MINOR 也可能包含破坏性变更，但会在 CHANGELOG 的 BREAKING 段落列清楚，并提供 godw-cli migrate --check 检查。

2. 数据库迁移

迁移文件在 migrations/，按编号顺序执行，记录在 schema_migration 表。

约定：迁移只做加法。

-- ✅ 允许
ALTER TABLE model ADD COLUMN IF NOT EXISTS owner TEXT NOT NULL DEFAULT '';
CREATE TABLE IF NOT EXISTS new_thing (...);
CREATE INDEX IF NOT EXISTS idx_x ON t(col);

-- ❌ 禁止（会在升级中途破坏旧版本）
DROP COLUMN owner;
ALTER COLUMN amount TYPE int;

需要删列时走三期：

  1. 停用（MINOR）：代码不再读写该列，DDL 保留。
  2. 观察（至少一个小版本）：确认没有外部系统依赖。
  3. 删除（MAJOR）：迁移文件里 DROP COLUMN。

检查是否有待执行迁移

godw-cli migrate --check --config config.yaml

退出码 0 表示已最新，1 表示有待执行。

3. 滚动升级顺序

# 1. 备份
pg_dump -Fc godw > backup/pre-$(date +%F).dump

# 2. 迁移（向前兼容：新表新列对旧代码无害）
kubectl apply -f migrate-job.yaml

# 3. worker（旧 worker 会把当前实例跑完再退出）
kubectl rollout restart deploy/godw-worker

# 4. server
kubectl rollout restart deploy/godw-server

为什么 worker 先于 server：新 schema 对旧 worker 是兼容的（只多了列/表），但新 server 可能写入新字段，旧 worker 不认识。先升数据面再升控制面，中间态最安全。

4. 兼容性矩阵

组件 可跨版本混跑 说明
server ↔ worker ±1 MINOR 通过数据库通信，只依赖 instance/task_instance 表结构
CLI ↔ server 任意 CLI 直连数据库，不经过 server
内嵌控制台 ↔ API 同二进制 前端与后端一起打包，不存在版本错配
任务卡 ↔ 执行器 无关 runner/ 是开发期工具，不参与运行

5. 弃用流程

  1. 标记弃用：接口返回 Deprecation 响应头 + 文档标注。
  2. 保留至少一个 MINOR 周期。
  3. 下一个 MAJOR 移除。

已弃用清单见 CHANGELOG.md 的 Deprecated 段。

6. 回滚

# 代码回滚
kubectl rollout undo deploy/godw-server

# 数据库：只有在迁移不可逆时才需要
pg_restore -d godw --clean --if-exists backup/pre-2026-11-11.dump

能回滚代码不等于能回滚数据。迁移里写了 DROP 的，回滚会丢数据——所以禁止在非 MAJOR 版本写 DROP。

7. 配置兼容

配置项只增不删。改名时保留旧名作为别名，并在启动日志打一条警告：

# 旧名（已弃用，将在 1.0 移除）
cache_ttl: 60
# 新名
semantic:
  cache_ttl_sec: 60

加载器按 新名 > 旧名 > 默认值 的顺序取值。

8. 状态兼容

instance.status 新增状态时必须保证旧代码能安全忽略。当前状态集：

queued → running → success
                 → failed
                 → blocked（连续失败达到阈值）

新增状态（如 canceled）时，旧版本会把它当作未知状态，只影响展示，不影响调度判定。
