E05 · 调度与执行 ｜ E06 · 质量与血缘

本组是整个系统最容易「看起来能跑、实际不可靠」的部分。所有任务都必须覆盖并发、崩溃、重复触发三类异常，不允许只实现happy path。

E05 调度与执行（20 人日）

T0501 · 实例模型与状态机 P0 2d

目标：任务状态机是整个平台的真相来源。 要点 - 状态枚举与 docs/02 第 3.1 节一致；所有迁移走 Transition(ctx, id, from, to, patch)，SQL 条件更新，影响行数 0 视为冲突并返回明确错误。 - 禁止任何 UPDATE ... SET state=? 无条件更新；禁止在业务代码里直接写 state 字符串，用常量 + 校验函数 CanTransit(from,to)。 - 状态迁移表驱动测试：合法迁移全通过、非法迁移全被拒（矩阵覆盖）。 - 终态（SUCCESS/FAILED/KILLED/SKIPPED/UPSTREAM_FAILED）不可再迁移（除人工重跑重置 attempt）。 产出：internal/scheduler/state.go、Transition 实现、状态图文档。 验收：并发 100 goroutine 对同一实例做同一迁移，只有 1 个成功；状态矩阵测试全绿。

T0502 · 依赖解析与就绪判定 P0 2d

目标：上游没成功，下游绝不启动。 要点 - 依据 pipeline_version.compiled 的拓扑序与入边，批量把 PENDING → READY（所有上游 ∈ {SUCCESS, SKIPPED}）；任一上游失败 → UPSTREAM_FAILED。 - 判定用一条 SQL 完成（NOT EXISTS 子查询），禁止逐实例循环查库。 - 支持「跨管道依赖」：sensor 节点等待另一管道成功（按 pipeline + bizdate 查询）。 - 每轮扫描限制批量（500 条）避免长事务。 产出：internal/scheduler/dag/resolver.go。 验收：1000 实例 / 10 层 DAG，一轮判定 ≤ 200ms；上游失败后 1 个调度周期内下游变 UPSTREAM_FAILED。

T0503 · 调度器主循环 P0 2.5d

目标：按 cron 稳定产生实例，且不重复。 要点 - 每秒 tick：计算 next_fire_at <= now 的管道 → 按 bizdate 生成实例；INSERT ... ON CONFLICT DO NOTHING 依赖唯一键去重。 - 多副本用 PG advisory lock 保证单活（pg_try_advisory_lock(hash)），持锁实例定期续期；失锁立即停止调度。 - cron 支持标准 5 段 + @daily/@hourly + 时区；用 robfig/cron/v3 解析，禁止自研。 - 记录 last_fire_at 与 next_fire_at，重启后从库恢复，不补跑历史（补跑走 backfill）。 - 提供「暂停/恢复调度」「立即触发」开关，暂停期间不生成实例。 产出：internal/scheduler/loop.go、cron.go。 验收：重启 10 次不产生重复实例；双副本只有一个在调度（日志验证）；暂停后不再新建实例。

T0504 · 队列与分发 P0 2d

目标：任务按优先级与资源组公平出队。 要点 - 出队：SELECT ... WHERE state='QUEUED' AND resource_group = ANY($1) ORDER BY priority, scheduled_at FOR UPDATE SKIP LOCKED LIMIT n。 - 资源组：每组配置 max_concurrency，分发前用计数（Redis 或 PG count）判断是否有空位；满则留在 READY。 - 优先级 1–9（1 最高），同优先级按 scheduled_at FIFO；支持「紧急插队」接口但记录审计。 - 分发与领取解耦：分发只改 READY→QUEUED，worker 才 QUEUED→RUNNING。 产出：internal/scheduler/queue/*、dispatch.go。 验收：1000 任务 5 并发槽位下无超发；高优先级任务先出队；SKIP LOCKED 下无重复领取。

T0505 · worker 租约与崩溃恢复 P0 2.5d

目标：worker 挂了任务不会永久卡住。 要点 - 领取时写 worker_id 与 lease_until = now + timeout；执行中每 15s 心跳续租。 - 回收器每 30s 扫描 state='RUNNING' AND lease_until < now()：attempt+1，未超上限则回 QUEUED（保留原 worker_id 供排查），超限则 FAILED（error_code=LEASE_EXPIRED）。 - 优雅退出：收到 SIGTERM 停止领新任务，等待在跑任务完成（上限 60s），超时后强制上报 FAILED(worker_shutdown) 以便重派。 - worker 注册表记录主机、版本、资源组、最后心跳，运维页可见。 产出：internal/executor/lease/*、recover.go、worker/registry.go。 验收：kill -9 worker 后 ≤ 60s 任务被重派并最终成功；SIGTERM 后不再领新任务。

T0506 · 任务执行器 P0 3d

目标：插件式执行各类节点。 要点 - Runner 接口见 docs/03 第 7 节；注册表按 type 分发。 - sqlrunner：渲染快照 → 逐条执行写入语句 → 采集 rows_read/rows_written/bytes/duration → 失败带 sql_snippet（前 500 字符）与引擎错误码。 - shellrunner：白名单命令 + 参数数组（禁止 sh -c 拼接）、超时强杀进程组、捕获 stdout/stderr 分流。 - httprunner：超时、重试、2xx 判定、响应体截断存储。 - subpipeline：同步等待子管道完成，传递参数，防止循环嵌套（深度上限 3）。 - 所有 runner 必须支持 ctx 取消，并在退出前调用 sink.Flush()。 产出：internal/executor/runner/*、注册表。 验收：每个 runner 有集成测试；SQL 超时后连接被真正取消；shell 超时后子进程无残留（ps 校验）。

T0507 · 重试与失败策略 P0 2d

目标：偶发失败自愈，真失败快速暴露。 要点 - 重试策略：max、interval、backoff: fixed|exponential、retry_on（错误码白名单：连接超时/死锁可重试，语法错误/权限拒绝不重试）。 - 失败进入 RETRY_WAIT，记录 next_retry_at，调度器扫描到期后回 QUEUED；attempt 达上限 → FAILED。 - 下游传播：节点 FAILED → 所有下游 UPSTREAM_FAILED；节点 SKIPPED（人工）→ 下游按 skipPolicy（allow|forbid）决定是否继续。 - 连续失败 N 次的管道自动暂停调度并告警（防止雪崩）。 产出：internal/scheduler/retry.go、policy.go。 验收：语法错误不重试、超时重试 3 次；下游在 1 个周期内标记 UPSTREAM_FAILED；连续失败触发暂停。

T0508 · 补数与重跑 P0 2.5d

目标：补历史数据是日常操作，必须安全。 要点 - backfill(pipeline, from, to, params)：按日期展开实例，受唯一键去重（已存在的跳过或按 --force 重置）。 - 并发控制：同日期间按 DAG 层级并行，跨日期按 max_concurrency 限流；提供进度查询（总数/成功/失败/待跑）。 - 重跑粒度：单节点、单节点+下游、整条管道；重跑保留历史 run，attempt++。 - 补数任务可暂停/终止；终止后已排队实例置 KILLED。 - 禁止对 prod 环境无确认的大范围补数（> 31 天需二次确认）。 产出：internal/scheduler/backfill/*、API。 验收：补 30 天数据无重复实例；终止后无新实例产生；进度接口数据与实际一致。

T0509 · 事件触发与传感器 P1 2d

目标：不只是定时，还能等数据到。 要点 - sensor 三种：文件（S3/本地路径存在且大小稳定）、表（源表分区出现或行数 > 0）、HTTP（轮询接口返回满足条件）。 - 轮询间隔、超时、退避可配；超时置 FAILED(sensor_timeout)。 - 事件触发：接收外部 webhook（带签名校验）→ 生成实例；支持「文件到达即触发」。 - 去重：同一事件 ID 幂等，重复投递不产生新实例。 产出：internal/pipeline/node/sensor/*、internal/api/http/webhook.go。 验收：文件 10s 后到达，sensor 在 2 个轮询周期内成功；重复 webhook 只触发一次。

T0510 · 资源组与配额 P1 1.5d

目标：大查询不饿死小任务。 要点 - 资源组维度：并发上限、单任务超时、连接池上限、可用引擎。 - 任务提交前校验配额；超限排队而非拒绝，排队超时（默认 30 分钟）置 FAILED(queue_timeout)。 - 采集每任务资源用量（CPU 时间、扫描字节），按管道聚合，为成本核算（T0808）提供数据。 产出：internal/scheduler/quota/*、用量采集。 验收：heavy 组打满时 default 组任务不受影响；用量数据可按管道汇总。

T0511 · 日志采集与实时流 P0 2d

目标：任务日志能实时看、能回溯。 要点 - 执行器按行采集，带 seq/ts/level，本地缓冲 200 行或 1s 批量写 run_log。 - SSE 推送：/instances/{id}/logs/stream，支持 Last-Event-ID 断点续传；任务结束后推送 state 事件并关闭。 - 日志脱敏：命中密码/token 正则的行替换为 ***。 - 归档：> 7 天日志压缩上传对象存储，DB 只留索引；查询归档走预签名 URL。 产出：internal/api/sse/logs.go、internal/obs/logstore/*。 验收：日志首行延迟 ≤ 1s；断线重连不丢不重；归档后仍可按 run 查询下载。

T0512 · SLA 与告警 P1 2d

目标：出问题主动通知，而不是等业务发现。 要点 - SLA 规则：必须在 HH:mm 前完成、最大执行时长、失败即告警、数据量为 0、同比波动 > X%。 - 告警渠道插件化：webhook、邮件、飞书、钉钉、企业微信；模板可配。 - 抑制与聚合：同一管道 5 分钟内同类告警合并；维护窗口内静默。 - 告警记录可查、可标记处理状态，避免重复打扰。 产出：internal/obs/alert/*、渠道实现、规则配置。 验收：超时 1 分钟内收到 webhook；重复告警被合并；静默窗口内不发。

E06 数据质量与血缘（14 人日）

T0601 · 质量规则 DSL P0 2d

目标：质量规则可配置、可复用、可解释。 要点 - 内置类型：not_null、unique、unique_combination、accepted_values、range、regex、referential（引用另一模型主键）、row_count_delta（环比/同比阈值）、custom_sql（返回违规行）。 - 规则编译为 SQL：违规计数 SELECT COUNT(*) FROM t WHERE NOT (expr)；抽样 SELECT * FROM t WHERE NOT (expr) LIMIT 20。 - 所有规则必须有 severity（block/warn/info）与 enabled；block 规则失败阻断下游。 - 支持字段级与表级（多列组合）规则；custom_sql 必须只读（禁止 DML 关键字，解析器校验）。 产出：internal/quality/compile.go、规则 schema。 验收：9 类规则各 2 个用例；custom_sql 含 DELETE 被拒；生成的 SQL 在四引擎可执行。

T0602 · 规则执行与结果 P0 2d

目标：每次跑数都留质量证据。 要点 - 质量节点作为 DAG 中独立节点执行，结果写 quality_result（通过率、违规数、样本、耗时）。 - 样本脱敏后存储（high 级 PII 打码），最多 20 行。 - 同一规则同一 bizdate 多次执行保留历史，取最新为当前状态。 - 提供趋势 API：近 30 天通过率、违规数曲线。 产出：internal/quality/runner.go、查询 API。 验收：违规时样本正确；趋势接口返回 30 个点；重复执行不覆盖历史。

T0603 · 质量门禁 P0 1.5d

目标：脏数据不流到下游。 要点 - block 规则失败 → 当前节点 FAILED(quality_block)，下游 UPSTREAM_FAILED；warn 只告警不阻断。 - 提供「强制放行」操作（需理由 + 审批记录），放行后下游继续并在数据上打标。 - 隔离表：可选把违规行写入 quarantine_<model>，便于修复重放。 产出：门禁逻辑、放行 API、隔离表写入。 验收：block 失败后下游确实未执行；放行后下游执行且审计有记录。

T0604 · 自动 Profiling 与规则推荐 P2 2d

目标：新表接入自动给一套基础规则。 要点 - 对表采样（≤10 万行）统计：空值率、唯一度、min/max、枚举 Top20、正则命中率。 - 推荐规则：唯一度=1 → unique；空值率=0 → not_null；枚举少 → accepted_values；数值 → range。 - 推荐结果以「建议」形式展示，人工确认后才启用，避免误报泛滥。 产出：internal/quality/profile.go、推荐 API。 验收：样例表推荐命中 ≥ 3 条有效规则；未确认的建议不参与执行。

T0605 · SQL 解析器接入 P0 2d

目标：为列级血缘提供 AST 能力。 要点 - 引入 pingcap/tidb/parser（MySQL 兼容），封装 Parse(sql) (StmtNode, error)；对不支持语法返回明确错误而非 panic。 - 统一封装 sqlparse 包，隔离第三方依赖，未来可替换为其他 parser。 - 处理 ?/$1 占位符；模板渲染后的 SQL 才解析（保留原始 SQL 供回溯）。 - 性能：单条 SQL 解析 ≤ 5ms；大 SQL（>100KB）限制并降级为表级血缘。 产出：internal/lineage/parser/parser.go、错误封装、基准测试。 验收：50 条真实业务 SQL 解析成功率 ≥ 95%；非法 SQL 返回结构化错误不 panic。

T0606 · 表级血缘 P0 1.5d

目标：知道每张表从哪来、到哪去。 要点 - 来源：管道节点 ref()/src() + write.model，发布时写入 lineage_edge（src_table → dst_table）。 - 同一管道重复发布需先删除旧边再写新边（按 pipeline_id 维度），避免残留。 - 查询 API：?table=&direction=up|down&depth=n，返回节点 + 边，前端直接渲染。 - 图规模大时限制 depth ≤ 5，超出提示。 产出：internal/lineage/graph/table.go、API。 验收：发布管道后血缘边正确；重新发布不产生重复边；上下游方向正确。

T0607 · 列级血缘 P0 3d

目标：改一列能知道影响哪些指标。 要点 - 遍历 AST：收集 TableRef（含 CTE、子查询、别名作用域）→ 解析 SelectField 的列引用 → 用作用域链解析到源表列。 - 处理：别名（a.id AS order_id）、表达式（SUM(amount) → 依赖 amount）、JOIN ... ON、UNION（逐分支合并）、SELECT *（回查模型 schema 展开）。 - 无法确定的映射（函数嵌套过深、动态 SQL）标记 confidence=low，保留表级边。 - 输出 column_map: {dst_col: [src_col...]} 存 lineage_edge.column_map。 产出：internal/lineage/parser/column.go、测试集。 验收：20 条含 CTE/JOIN/UNION 的 SQL 列映射准确率 ≥ 90%；SELECT * 能展开；低置信度被标记。

T0608 · 血缘图存储与查询 P0 1.5d

目标：查询要快，图要大。 要点 - 邻接表存 PG，热点路径内存缓存（LRU，5 分钟 TTL）；递归查询用 WITH RECURSIVE 限制深度。 - 提供批量查询：一次返回多张表的血缘，供前端一次渲染。 - 节点去重、边去重；支持按 workspace 过滤。 - 提供 graph JSON 格式（nodes/edges）与 DOT 导出。 产出：internal/lineage/graph/store.go、cache。 验收：1 万条边下 depth=3 查询 ≤ 300ms；缓存命中率 > 80%。

T0609 · 影响分析 P0 1.5d

目标：变更前知道会炸哪些下游。 要点 - 输入表名/列名 → BFS 下游 → 输出受影响表、指标、看板、调度管道清单。 - 结合 metric 与 dashboard 反向索引（指标依赖 dataset 的 base_model，看板依赖 dataset）。 - 评估风险等级：影响生产 ADS 表或对外看板 → high；仅中间层 → medium。 - 提供「变更预检」API，供 T0306 发布前调用，high 风险需显式确认。 产出：internal/lineage/impact.go、API。 验收：删除 DWD 列能列出 3 层下游与 2 个看板；风险等级判定符合规则。

T0610 · 血缘前端接口联调 P1 1d

目标：接口先稳定，前端才好做。 要点 - 约定 graph 数据结构：{nodes:[{id,type,layer,name,meta}], edges:[{source,target,columns,confidence}]}。 - 支持按层着色、按表聚焦（只显示 N 跳）、列级展开/收起。 - 提供「路径查询」：两表之间的所有路径，最多 10 条。 产出：graph API、路径查询、接口文档。 验收：前端用 mock 数据即可完成渲染；路径查询返回结果不含环。
